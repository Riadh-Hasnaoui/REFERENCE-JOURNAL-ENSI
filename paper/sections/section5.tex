\section{Trade-off Framework for Paradigm Selection}
\label{sec:tradeoffs}

Selecting an appropriate repository representation paradigm requires reasoning
over five operational dimensions: (D1)~\emph{Semantic Precision},
(D2)~\emph{Token Budget}, (D3)~\emph{Construction Latency},
(D4)~\emph{Context Freshness}, and (D5)~\emph{Scalability \& Update Cost}.

\subsection{D1 vs.\ D2: Semantic Precision vs.\ Token Efficiency}
Repoformer~\cite{wu2024repoformer} (PAR-2) applies a selective retrieval
gate that discards low-relevance cross-file snippets, reducing token consumption
by up to 40\% with minimal precision loss.  LongCodeZip~\cite{shi2025longcodezip}
(PAR-6) achieves extreme compression ratios via a learned token-merging
strategy at the cost of a non-trivial encoding overhead.

\subsection{D3 vs.\ D4: Latency vs.\ Context Freshness}
Graph-based paradigms (PAR-3) and embedding indices (PAR-1) amortise
construction cost via offline indexing, but are exposed to \emph{stale
context} when the repository evolves.  HumanEvo~\cite{zheng2025humanevo}
quantifies this bias: evaluating code-completion systems on snapshots rather
than the true head commit inflates accuracy by 10–61\%.  PAR-4 (execution
traces) and PAR-7 (agentic exploration) eliminate stale context at the price
of real-time latency.

\subsection{D5: Scalability \& Update Cost}
Updating a call graph (PAR-3, CodexGraph~\cite{liu2025codexgraph}) after a
single-file edit in a 10\,000-file repository requires an incremental
re-traversal that can take seconds.  Adaptive memory (PAR-5,
CodeMEM~\cite{wang2026codemem}) avoids full rebuilds by maintaining
function-level patches to the memory store.
