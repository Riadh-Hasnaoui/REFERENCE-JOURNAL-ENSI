\title{How Do LLM-Based Agents Represent Code Repositories? A Systematic
       Review, Taxonomy, and Comparative Evaluation}

\author{Anonymous}
\affiliation{%
  \institution{Anonymous Institution}
  \country{Anonymous Country}}
\email{anonymous@institution.edu}

\begin{abstract}
Modern software-engineering tasks --- code completion, generation, bug repair,
test synthesis, and refactoring --- increasingly rely on large language models
(LLMs) that must comprehend entire \emph{code repositories}.  Despite a
rapidly growing literature, no unified conceptual framework has yet been
proposed to compare the diverse strategies by which these models acquire,
structure, and exploit repository-level context.

This paper presents a \emph{Systematic Literature Review} (SLR) following the
Kitchenham guidelines, covering \textbf{168 peer-reviewed studies} published
between 2020 and early~2026 and selected through a rigorous
inclusion/exclusion protocol.  From this corpus we derive a
\textbf{seven-paradigm taxonomy} (\textbf{PAR-1}--\textbf{PAR-7}) organised
along \textbf{ten structural dimensions} (\textbf{D1}--\textbf{D10}).  We
further provide a comparative evaluation of representative systems against 25
public benchmarks, identify key research gaps, and outline a research agenda
for repository-aware LLM-based software engineering.
\end{abstract}

\section{Introduction}
\label{sec:intro}
%%══════════════════════════════════════════════════════════════════════════════

The advent of large language models (LLMs) has transformed automated software
engineering (SE).  Tools such as \toolname{SWE-agent}~\cite{yang2024sweagent},
\toolname{OpenHands}~\cite{wang2025openhands}, and
\toolname{MetaGPT}~\cite{hong2023metagpt} demonstrate that LLMs, when given
appropriate context, can resolve real-world GitHub issues, generate entire
features, and repair complex bugs.  However, the performance of these systems
depends critically on \emph{how they represent the code repository}: what
context they extract, at what granularity, and through what mechanism.

Existing surveys~\cite{hou2024llmsslr,jiang2026surveyllm,tao2026ragsurvey,%
zhang2026surveyllmse} provide broad overviews but lack a fine-grained
\emph{taxonomy} of context-representation strategies.  Practitioners therefore
face a fragmented landscape: dense embedding models, retrieval-augmented
generation (RAG) pipelines, graph-structured representations, execution-trace
oracles, memory architectures, compression schemes, and full agentic loops
all co-exist without a common reference frame.

\textbf{Contributions.}  This paper makes the following contributions:
\begin{enumerate}[leftmargin=*,topsep=2pt,itemsep=1pt]
  \item A \emph{rigorous SLR protocol} (Kitchenham~\cite{kitchenham2004slr})
        applied to 168 primary studies published 2020--2026
        (Section~\ref{sec:methodology}).
  \item A \emph{seven-paradigm taxonomy} (PAR-1--PAR-7) characterised along
        \emph{ten structural dimensions} (D1--D10), including a refined
        dimension \textbf{D10: Training Dependency} that distinguishes
        zero-shot, RAG-only, lightweight fine-tuning, and full reinforcement
        learning workflows (Section~\ref{sec:taxonomy}).
  \item A \emph{cross-paradigm disambiguation} resolving recurring confusions
        between PAR-4 and PAR-7, and between PAR-5 and PAR-7
        (Section~\ref{subsec:disambiguation}).
  \item A \emph{comparative evaluation} of representative systems on 25
        public benchmarks (Section~\ref{sec:evaluation}).
  \item A \emph{research agenda} identifying open challenges and future
        directions (Section~\ref{sec:discussion}).
\end{enumerate}

\section{Methodology}
\label{sec:methodology}
%%══════════════════════════════════════════════════════════════════════════════

We follow Kitchenham's guidelines for conducting systematic literature reviews
in software engineering~\cite{kitchenham2004slr}.

\subsection{Research Questions}

\begin{description}[leftmargin=2em,topsep=2pt,itemsep=2pt]
  \item[RQ1] What are the distinct paradigms by which LLM-based systems
             represent code repositories?
  \item[RQ2] Along what structural dimensions do these paradigms differ?
  \item[RQ3] Which paradigms achieve the best trade-off across SE objectives,
             benchmarks, and training cost?
  \item[RQ4] What are the open challenges in repository-level LLM-based SE?
\end{description}

\subsection{Search Strategy}

We queried ACM Digital Library, IEEE Xplore, Semantic Scholar, and arXiv
using the string:
\begin{quote}\small
\texttt{("repository-level" OR "repo-level" OR "cross-file") AND}\\
\texttt{("LLM" OR "large language model" OR "language model") AND}\\
\texttt{("code" OR "software engineering")}
\end{quote}

\subsection{Inclusion and Exclusion Criteria}

\textbf{Inclusion.}
\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=1pt]
  \item \textbf{IC1} --- The study proposes or evaluates a method for
    extracting or structuring \emph{repository-level context} to feed an LLM
    in an automated SE task (examples: RAG cross-file, dependency graphs,
    hierarchical summaries, agent memories, execution traces).
  \item \textbf{IC2} --- The study targets at least one of seven SE
    objectives: code completion (O1), code generation (O2), code search (O3),
    bug fixing (O4), refactoring/translation (O5), test generation (O6), or
    code review (O7).
  \item \textbf{IC3} --- The work appears in a peer-reviewed venue of
    appropriate standing (ICSE, FSE, ASE, ISSTA, PLDI, NeurIPS, ICML, ICLR,
    ACL, EMNLP, NAACL, AAAI, TSE, TOSEM, EMSE, MSR, SANER, FORGE, \ldots)
    or is an arXiv pre-print satisfying the grey-literature exception
    (${\ge}50$ citations, or public artefacts on a standardised benchmark).
\end{itemize}

\textbf{Exclusion.}
\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=1pt]
  \item \textbf{EC1} --- Pure LLM architecture/pre-training papers without a
    repository-context mechanism.
  \item \textbf{EC2} --- Works operating exclusively at function or snippet
    level (no cross-file context).
  \item \textbf{EC3} --- Position papers or purely theoretical contributions
    without empirical evaluation.
  \item \textbf{EC4} --- Secondary studies (surveys, SLRs, meta-analyses)
    retained only in the Related Work section for snowballing.
  \item \textbf{EC5} --- Highly domain-specific applications (cybersecurity,
    smart contracts, hardware design).
  \item \textbf{EC6} --- Duplicate versions of the same work (only the most
    recent peer-reviewed version is retained).
\end{itemize}

\subsection{Study Selection and Data Extraction}

After deduplication, an initial pool of 934~studies was screened by two
independent reviewers; disagreements were resolved by a third reviewer.
The final corpus comprises \textbf{168 primary studies}.  Each study was
annotated with the ten taxonomy dimensions described in
Section~\ref{sec:taxonomy}.

\section{A Seven-Paradigm Taxonomy of Repository-Level Context Representation}
\label{sec:taxonomy}
%%══════════════════════════════════════════════════════════════════════════════

\subsection{The Ten-Dimension Analysis Framework}
\label{subsec:dimensions}

Every primary study in our corpus is characterised along ten dimensions.
Table~\ref{tab:dimensions} provides an overview; each dimension is described
below.

\begin{table*}[t]
  \caption{The ten structural dimensions (D1--D10) used to characterise each
           paradigm.  D10 was revised in this review: the former label
           \emph{Fine-Tuning Requirements} has been replaced by
           \emph{Training Dependency}, which more accurately captures the
           full spectrum from zero-shot inference to full reinforcement
           learning.}
  \label{tab:dimensions}
  \small
  \begin{tabular}{@{}llp{9cm}@{}}
    \toprule
    \textbf{Dim.} & \textbf{Label} & \textbf{Value range (representative values)} \\
    \midrule
    D1  & Representation Modality   & Dense vector; sparse text/BM25; symbolic graph; execution trace; NL summary \\
    D2  & Context Granularity       & Token; statement; function; file; cross-file; repository-wide \\
    D3  & Context Source            & Static analysis; runtime execution; version history; external KB \\
    D4  & Retrieval Mechanism       & None; lexical (BM25/TF-IDF); dense (FAISS/ANN); graph traversal; agent-driven \\
    D5  & Temporal Awareness        & Static; dynamic (online); hybrid \\
    D6  & Primary SE Objective      & O1 completion; O2 generation; O3 search; O4 bug fixing; O5 refactoring; O6 testing; O7 review \\
    D7  & Multi-language Support    & Single language; multiple languages \\
    D8  & Context Window Strategy   & Naive truncation; selective filtering; hierarchical compression; adaptive summarisation \\
    D9  & Evaluation Protocol       & Task-metric (EM, BLEU, pass@k); benchmark suite; human study \\
    D10 & \textbf{Training Dependency} & \textbf{Zero-shot} (no task-specific training); \textbf{RAG-only} (retrieval, no fine-tuning); \textbf{Lightweight FT} (LoRA / adapter / instruction tuning); \textbf{Full RL} (reinforcement learning from execution rewards) \\
    \bottomrule
  \end{tabular}
\end{table*}

\paragraph{D10 --- Training Dependency (formerly \emph{Fine-Tuning Requirements}).}
The original label \emph{Fine-Tuning Requirements} in earlier drafts of this
taxonomy conflated two orthogonal concerns: (i)~whether any task-specific
parameter update is required at all, and (ii)~the computational and data cost
of that update.  We therefore adopt the label \textbf{Training Dependency} and
define four ordered levels:

\begin{description}[leftmargin=2em,topsep=2pt,itemsep=2pt]
  \item[\textit{Level~0 --- Zero-shot.}] The system uses a frozen, pre-trained
    LLM with no task-specific adaptation.  The repository is represented
    entirely through prompt engineering and context assembly.  Examples:
    \toolname{RepoCoder}~\cite{zhang2023repocoder},
    \toolname{CodexGraph}~\cite{liu2025codexgraph}.

  \item[\textit{Level~1 --- RAG-only.}] Retrieval components (indexing,
    embedding, ranking) are trained or fine-tuned, but the backbone LLM
    remains frozen.  The representation is encoded in the retrieval index
    rather than in model weights.  Examples:
    \toolname{ReACC}~\cite{lu2022reacc},
    \toolname{Repoformer}~\cite{wu2024repoformer},
    \toolname{SECRET}~\cite{gu2025secret}.

  \item[\textit{Level~2 --- Lightweight FT.}] The backbone LLM is adapted via
    parameter-efficient methods (LoRA, adapter layers, or targeted instruction
    tuning) on repository-related data.  This includes cross-file context
    alignment~\cite{li2025alignllms} and preference-guided
    tuning~\cite{gao2024prefguided}.

  \item[\textit{Level~3 --- Full RL.}] The LLM is updated through
    reinforcement learning with rewards derived from code execution or test
    outcomes.  This is the most expensive tier and yields models that learn to
    \emph{navigate} the repository as an environment.  Examples:
    \toolname{SWE-RL}~\cite{wei2025swerl},
    \toolname{RLCoder}~\cite{wang2025rlcoder},
    \toolname{IRCoCo}~\cite{li2024ircoco}.
\end{description}

This revised definition enables direct, comparable positioning of all 168
primary studies on a single axis without conflating prompt-level,
retrieval-level, and training-level choices.

%%──────────────────────────────────────────────────────────────────────────────
\subsection{PAR-1: Repository-Level Code Embedding \& Dense Representation}
\label{subsec:par1}
%%──────────────────────────────────────────────────────────────────────────────

\paragraph{Definition.}
PAR-1 systems represent the repository as a collection of \emph{dense
continuous vectors} produced by a code-pretrained encoder.  A shared embedding
space allows semantic similarity search across the entire codebase.  The
representation is static: it is computed offline and stored in a vector index.

\paragraph{Canonical works.}
\toolname{CodeBERT}~\cite{feng2020codebert} and
\toolname{UniXcoder}~\cite{guo2022unixcoder} establish the bimodal
(code + natural language) pretraining paradigm.
\toolname{LongCoder}~\cite{guo2023longcoder} extends the context window to
handle longer code sequences.
More recently, contrastive learning with hard negative
mining~\cite{fan2025hardneg} and context
alignment~\cite{li2025alignllms,sohrabizadeh2025nemotron} improve retrieval
precision for cross-file scenarios.
Repository-level prompt generation~\cite{shrivastava2023repoprompt} and
hierarchical context pruning~\cite{zhang2025hierctxpruning} address the
token-budget problem at the prompt-assembly layer.

\paragraph{Dimension profile.}
D1~=~Dense vector; D2~=~Function/file; D3~=~Static analysis;
D4~=~Dense (FAISS/ANN); D5~=~Static; D6~=~O1, O3;
D7~=~Multi; D8~=~Selective filtering; D9~=~Benchmark (CrossCodeEval, RepoBench);
\textbf{D10~=~RAG-only} (embedding models trained; backbone LLM frozen) or
\textbf{Lightweight FT} for context-alignment variants.

%%──────────────────────────────────────────────────────────────────────────────
\subsection{PAR-2: Retrieval-Augmented Context Construction (RAG cross-file)}
\label{subsec:par2}
%%──────────────────────────────────────────────────────────────────────────────

\paragraph{Definition.}
PAR-2 encompasses systems that \emph{retrieve} relevant cross-file context at
inference time and prepend it to the LLM's prompt.  The repository is not
persistently embedded into model weights; rather, it is encoded in a retrieval
index (sparse or dense) that is queried on demand.

\paragraph{Canonical works.}
\toolname{ReACC}~\cite{lu2022reacc} introduces the retrieve-then-complete
pipeline.  \toolname{RepoCoder}~\cite{zhang2023repocoder} iterates retrieval
and generation in multiple rounds.  \toolname{CodeRAG}~\cite{zhang2025coderag}
and \toolname{HyRACC}~\cite{li2025hyracc} combine sparse and dense signals.
Industry deployments such as WeChat's RAG pipeline~\cite{yang2025wechat} and
comparative analyses~\cite{wang2025ragorfine,yang2025empiricalrag} validate
PAR-2 approaches at scale.  Specialised PAR-2 variants target
completion~\cite{ding2024cocomic,liang2024repogenix,shen2025adaptiveseg,%
wu2024repoformer,rahman2025positionchunk,sedov2025contextfilter,%
yusuf2025granularity},
type context~\cite{pan2025catcoder},
API inference~\cite{deng2025internalapi},
issue-commit linking~\cite{huang2025issuecommit},
and code quality improvement~\cite{abtahi2025staticcode,olewicki2026reviewassist}.

\paragraph{Dimension profile.}
D1~=~Sparse + Dense; D2~=~Function/cross-file; D3~=~Static analysis;
D4~=~BM25 + dense; D5~=~Static (one-shot) or iterative;
D6~=~O1, O2; D7~=~Multi; D8~=~Filtering / chunking;
D9~=~Benchmark (CrossCodeEval, RepoBench, DevEval, SWE-bench);
\textbf{D10~=~Zero-shot or RAG-only}.

%%──────────────────────────────────────────────────────────────────────────────
\subsection{PAR-3: Graph-Based \& Structural Representation}
\label{subsec:par3}
%%──────────────────────────────────────────────────────────────────────────────

\paragraph{Definition.}
PAR-3 systems represent the repository as a \emph{formal graph structure}
derived from static program analysis.  Unlike PAR-1 (continuous embeddings) or
PAR-2 (textual chunks), the context here is an explicit relational structure
that captures program semantics beyond surface form.

\paragraph{Graph sub-types.}
PAR-3 covers five families of structural representations, often used in
combination:

\begin{description}[leftmargin=2em,topsep=2pt,itemsep=3pt]
  \item[\textit{Abstract Syntax Tree (AST).}]
    Captures the syntactic structure of individual files or functions.
    Used in \toolname{CodeMEM}~\cite{wang2026codemem} (AST-guided adaptive
    memory), \toolname{CoSrch}~\cite{xu2025cosrch} (syntactic code search),
    and the structural analysis in~\cite{leanh2026codenotnl}.

  \item[\textit{Control Flow Graph (CFG).}]
    Encodes intra-procedural control paths.  Leveraged in
    \toolname{SAINT}~\cite{pan2025saint} (integration test generation) and
    program-repair
    approaches~\cite{parasaram2025factselect,wang2023rapgen}.

  \item[\textit{Call Graph.}]
    Represents inter-procedural dependencies across the repository.
    \toolname{RepoScope}~\cite{liu2025reposcope} builds a call-chain-aware
    multi-view context; \toolname{GRACE}~\cite{wang2025grace} fuses call
    graphs with retrieval; \toolname{AskGraph}~\cite{yang2025askgraph}
    queries dependency-aware call graphs via LLM-generated Cypher queries.

  \item[\textit{Data Flow Graph (DFG).}]
    Tracks variable definitions and uses across statements.
    \toolname{GraphCodeBERT}~\cite{guo2021graphcodebert} incorporates DFGs
    into pretraining.
    \toolname{Dataflow-Guided RAG}~\cite{cheng2024dataflowrag} uses DFGs to
    select the most relevant cross-file context.
    \toolname{AlphaTrans}~\cite{ibrahimzada2025alphatrans} exploits data flow
    for compositional code translation.

  \item[\textit{Knowledge Graph (KG) / Code Graph Database.}]
    Encodes entities (classes, methods, files) and semantic relations (calls,
    inherits, imports) in a property graph.
    \toolname{CodexGraph}~\cite{liu2025codexgraph} bridges LLMs with a Neo4j
    code graph database; \toolname{RepoGraph}~\cite{ouyang2025repograph}
    builds a repository-level code graph;
    \toolname{RepoChat}~\cite{abedu2025repochat} and
    \toolname{Synergizing LLMs with KGs}~\cite{abedu2026llmskg} use KGs for
    Q\&A over repositories;
    \toolname{Knowledge Graph Code Generation}~\cite{athale2025kgcode}
    drives generation from a KG.
    \toolname{CGM}~\cite{tao2025cgm} trains an LLM on top of a graph
    backbone.
    \toolname{RPG}~\cite{luo2026rpg} and
    \toolname{RPG-Encoder}~\cite{luo2026rpgencoder} construct planning graphs
    for codebase generation at scale.
\end{description}

\paragraph{Additional PAR-3 systems.}
\toolname{GraphCoder}~\cite{liu2024graphcoder},
\toolname{RepoHyper}~\cite{phan2025repohyper},
\toolname{GRACG}~\cite{fedorov2025gracg},
\toolname{LocAgent}~\cite{chen2025locagent},
\toolname{Issue Localization via Code Graph}~\cite{jiang2025issueloc},
\toolname{LiSSA}~\cite{fuchss2025lissa},
\toolname{Impact Analysis with PDGs}~\cite{yan2024impactanalysis},
\toolname{Artifact-Integrated Bug Localisation}~\cite{feng2025buglocarti},
\toolname{Cross-Lingual Semantic Graphs}~\cite{jiang2024crosslinggraph},
\toolname{MGS3}~\cite{li2025mgs3},
\toolname{Knowledge-Enhanced Bug Localisation}~\cite{li2025knowledgebug}, and
\toolname{Fact Selection in Program Repair}~\cite{parasaram2025factselect}.

\paragraph{Dimension profile.}
D1~=~Symbolic graph (AST / CFG / Call~Graph / DFG / KG);
D2~=~Cross-file/repository; D3~=~Static analysis;
D4~=~Graph traversal / graph query (Cypher / GNN);
D5~=~Static; D6~=~O2, O3, O4, O5; D7~=~Varies;
D8~=~Structural pruning;
D9~=~Benchmark (SWE-bench, CrossCodeEval, DevEval);
\textbf{D10~=~Zero-shot to Lightweight FT}
(KG querying may be zero-shot; GNN-augmented encoders require fine-tuning).

%%──────────────────────────────────────────────────────────────────────────────
\subsection{PAR-4: Execution \& Dynamic Representation}
\label{subsec:par4}
%%──────────────────────────────────────────────────────────────────────────────

\paragraph{Definition.}
PAR-4 systems derive context from \emph{runtime artefacts}: test execution
traces, compiler feedback, interpreter states, or differential execution
signals.  This dynamic information complements the static structure exploited
by PAR-1 through PAR-3.  Crucially, PAR-4 adopts a \textbf{passive,
observational} stance: the system \emph{records} what happens when the code
is run, but does not autonomously decide what to run next.

\paragraph{Canonical works.}
\toolname{IRCoCo}~\cite{li2024ircoco} uses immediate execution rewards to
guide reinforcement-learning-based code completion.
\toolname{Iterative Refinement with Compiler Feedback}~\cite{bi2024iterrefine}
injects compiler error messages as dynamic context.
\toolname{Rete}~\cite{parasaram2023rete} learns namespace representations
from runtime program repair traces.
\toolname{Trace}~\cite{tu2025trace} extracts context from test execution
traces to repair failing tests.
\toolname{RAP-Gen}~\cite{wang2023rapgen} retrieves analogous patches and uses
execution outcomes to rank repairs.
\toolname{Merge Conflict Resolution}~\cite{zhang2022mergeconflict} leverages
execution-validated context for textual and semantic conflicts.
\toolname{Rust Issue Resolution}~\cite{xiang2026rustissue} uses compilation
feedback to iteratively refine agent actions.
\toolname{SWE-Gym}~\cite{pan2025swegym} provides a training environment in
which agents receive execution-based rewards.

\paragraph{Dimension profile.}
D1~=~Execution trace / dynamic signal; D2~=~Cross-file/module;
D3~=~Runtime execution; D4~=~None (passive recording); D5~=~Dynamic;
D6~=~O4, O5, O6; D7~=~Single or multi; D8~=~Trace filtering;
D9~=~Benchmark (SWE-bench, ISSTA suites);
\textbf{D10~=~Lightweight FT or Full RL}
(rewards derived from code execution).

%%──────────────────────────────────────────────────────────────────────────────
\subsection{PAR-5: Memory-Augmented Context}
\label{subsec:par5}
%%──────────────────────────────────────────────────────────────────────────────

\paragraph{Definition.}
PAR-5 systems persist and retrieve structured or unstructured \emph{episodic
memory} about past interactions with a code repository.  The defining
characteristic is that \textbf{memory is the primary representational
structure: the context \emph{is} the memory}.  Memory buffers accumulate
facts, decisions, file summaries, or code snippets gathered from prior
inference steps, and selectively retrieve the most relevant items for each
new query.

\paragraph{Canonical works.}
\toolname{CodeMEM}~\cite{wang2026codemem} maintains an AST-guided adaptive
memory that grows iteratively as the agent generates code.
\toolname{LingmaAgent}~\cite{ma2025lingmaagent} combines a hierarchical file
summary memory with a semantic search index for issue resolution.
\toolname{Prometheus}~\cite{pan2026prometheus} manages long-horizon codebase
navigation by persisting a working memory of explored code regions.
\toolname{SWE-Exp}~\cite{chen2025sweexp} introduces experience-driven memory
that stores successful resolution trajectories for reuse.

\paragraph{Dimension profile.}
D1~=~NL summary + structured memory; D2~=~Repository-wide (episodic);
D3~=~Static + prior interaction; D4~=~Dense + temporal retrieval;
D5~=~Dynamic (growing memory); D6~=~O2, O4; D7~=~Multi;
D8~=~Memory consolidation / eviction;
D9~=~Benchmark (SWE-bench, FEA-Bench);
\textbf{D10~=~Zero-shot or Lightweight FT}
(memory architecture often orthogonal to LLM training).

%%──────────────────────────────────────────────────────────────────────────────
\subsection{PAR-6: Compression \& Summarisation}
\label{subsec:par6}
%%──────────────────────────────────────────────────────────────────────────────

\paragraph{Definition.}
PAR-6 systems cope with the finite context-window budget by
\emph{compressing} or \emph{summarising} the repository into a more compact
representation before passing it to the LLM.  The compressed representation
replaces the raw source in the prompt.

\paragraph{Canonical works.}
\toolname{LongCodeZip}~\cite{shi2025longcodezip} learns to compress long code
contexts for code LLMs via differentiable summarisation.
\toolname{SWE-Pruner}~\cite{wang2026swepruner} adaptively prunes the
repository context during agentic issue resolution.
\toolname{CodeS}~\cite{zan2025codes} generates multi-layer sketches
(NL $\to$ API $\to$ code) as a hierarchical compressed representation.
\toolname{Hierarchical Repository Summarisation}~\cite{dhulshette2025hiersumm}
compresses business-level codebases with local LLMs.
\toolname{Zero-Shot Cross-Domain Code Search}~\cite{liang2025zeroshot}
demonstrates that summarisation-based representations can transfer across
programming languages without fine-tuning.
\toolname{Code Summarisation Beyond Function Level}~\cite{makharev2025codesumm}
extends summarisation to module and repository granularity.
\toolname{Semantic Augmentation of Prompts}~\cite{ahmed2024semanticaug}
injects NL summaries of code artefacts into prompts.
\toolname{Natural Language Summarisation for Bug Localisation}~\cite{oskooei2025nlsumm}
and \toolname{Context Engineering for AI Agents}~\cite{mohsenimofidi2026contexteng}
demonstrate PAR-6 for microservice bug localisation and agentic open-source
tasks respectively.
\toolname{ArtifactSync}~\cite{alor2026artifactsync} uses hierarchical change
impact summaries for repository synchronisation.

\paragraph{Dimension profile.}
D1~=~NL summary / compressed token sequence; D2~=~Module/repository;
D3~=~Static + summarisation model; D4~=~Semantic filtering;
D5~=~Static; D6~=~O1, O2, O4, O7; D7~=~Multi;
D8~=~Adaptive summarisation;
D9~=~Benchmark (CrossCodeEval, SWE-bench);
\textbf{D10~=~Zero-shot or Lightweight FT}
(summarisation models may require instruction tuning).

\subsection{PAR-7: Agentic \& Iterative Context Exploration}
\label{subsec:par7}
%%──────────────────────────────────────────────────────────────────────────────

\paragraph{Definition.}
PAR-7 systems employ an LLM as an autonomous \emph{agent} that \textbf{actively
explores} the repository through a loop of observation, reasoning, and action.
Unlike PAR-4 (which passively records execution traces) and PAR-5 (where
memory \emph{is} the representation), in PAR-7 the agent is the primary
processing unit and memory, graphs, traces, and retrieval are \textbf{tools}
or \textbf{components} of a larger agentic pipeline.

\paragraph{Canonical works.}
\toolname{SWE-agent}~\cite{yang2024sweagent} designs an agent--computer
interface that gives the LLM direct shell access to the repository.
\toolname{OpenHands}~\cite{wang2025openhands} generalises the interface to a
platform for generalist software development agents.
\toolname{MetaGPT}~\cite{hong2023metagpt} orchestrates multiple specialised
agents via a shared message bus.
\toolname{CodePlan}~\cite{bairi2024codeplan} uses LLM-based planning to
decompose multi-file changes into atomic edit operations.
\toolname{AutoCodeRover}~\cite{zhang2024autocoderover} combines abstract
syntax tree navigation with spectrum-based fault localisation.
\toolname{SWE-Search}~\cite{antoniades2024swesearch} applies Monte Carlo Tree
Search to navigate the space of repository edits.
\toolname{RepairAgent}~\cite{bouzenia2025repairagent} is a fully autonomous
agent for LLM-based program repair.
\toolname{SWE-RL}~\cite{wei2025swerl} trains an agentic LLM via reinforcement
learning on open software evolution tasks.
\toolname{Nemotron-CORTEXA}~\cite{sohrabizadeh2025nemotron} improves
localisation diversity in agentic workflows.
Other notable systems include:
\toolname{AgentFL}~\cite{qin2025agentfl},
\toolname{OrcaLoca}~\cite{yu2025orcaloca},
\toolname{LocAgent}~\cite{chen2025locagent},
\toolname{CodeAgent}~\cite{zhang2024codeagent},
\toolname{ChatUniTest}~\cite{chen2024chatunitest},
\toolname{CoverUp}~\cite{altmayer2025coverup},
\toolname{CITYWALK}~\cite{zhang2025citywalk},
\toolname{KTester}~\cite{li2026ktester},
\toolname{LSPRAG}~\cite{go2025lsprag},
\toolname{SWE-Debate}~\cite{li2025swebdebate},
\toolname{SWE-GPT}~\cite{ma2025swegpt},
\toolname{Tool-integrated RL}~\cite{ma2025toolrl},
\toolname{Issue2Test}~\cite{nashid2026issue2test},
\toolname{RefAgent}~\cite{oueslati2026refagent},
\toolname{SpecRover}~\cite{ruan2025specrover},
\toolname{Divide-and-Conquer}~\cite{wang2025divideconquer},
\toolname{RLCoder}~\cite{wang2025rlcoder},

D1~=~Action sequence / multi-modal (text + tool calls);
D2~=~Repository-wide; D3~=~Static + runtime + interactive;

\textbf{D10~=~Zero-shot to Full RL}
(spans the full training dependency spectrum).

\subsection{Cross-Paradigm Disambiguation}
\label{subsec:disambiguation}
%%──────────────────────────────────────────────────────────────────────────────

Two pairs of paradigms have been repeatedly conflated in the literature.  We
provide explicit disambiguation criteria validated against the primary corpus.

\subsubsection{PAR-4 vs.\ PAR-7: Passive Trace Recording vs.\ Active
               Repository Exploration}
\label{subsubsec:par4vpar7}

Both PAR-4 and PAR-7 interact with the live code environment, which creates
the superficial impression that they are variants of the same idea.  The key
distinction lies in the \emph{locus of decision-making}:

\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=2pt]
  \item \textbf{PAR-4 --- Passive representation via execution traces.}  The
    system observes the output of a \emph{pre-determined} execution (a test
    run, a compiler pass, a static analyser).  The LLM itself does not decide
    \emph{what to run} or \emph{where to look next}; it merely receives the
    resulting trace as additional context.  The representation is
    \emph{observation-driven}: inputs are fixed, observations are recorded,
    and the LLM reasons over them in a single step (or a bounded number of
    refinement steps triggered by the same fixed oracle).
    Representative systems: \toolname{IRCoCo}~\cite{li2024ircoco},
    \toolname{Iterative Refinement with Compiler Feedback}~\cite{bi2024iterrefine},
    \toolname{Trace}~\cite{tu2025trace},
    \toolname{SWE-Gym}~\cite{pan2025swegym}.

  \item \textbf{PAR-7 --- Active exploration via autonomous agents.}  The LLM
    decides at each step \emph{which file to read, which test to run, which
    tool to invoke, and which patch to apply}.  The context is dynamically
    constructed by the agent's own policy; the repository is an
    \emph{environment} the agent navigates, not a passive information source.
    The exploration is \emph{open-ended}: the agent may issue hundreds of
    distinct tool calls before converging on a solution.
    Representative systems: \toolname{SWE-agent}~\cite{yang2024sweagent},
    \toolname{AutoCodeRover}~\cite{zhang2024autocoderover},
    \toolname{SWE-Search}~\cite{antoniades2024swesearch},
    \toolname{RepairAgent}~\cite{bouzenia2025repairagent}.
\end{itemize}

\noindent\textbf{Classification rule.}  A study belongs to PAR-4 if execution
feedback is a fixed, externally determined \emph{input signal}.  It belongs to
PAR-7 if the LLM autonomously \emph{decides} which executions to trigger and
acts on the results through an open-ended decision loop.  Studies that exhibit
both properties (e.g., RL agents trained with execution rewards but evaluated
in a fixed harness) are primarily classified in PAR-7 and tagged as
\emph{PAR-4-hybrid} in dimension D3.

\subsubsection{PAR-5 vs.\ PAR-7: Memory as Primary Structure vs.\ Memory as
               Pipeline Component}
\label{subsubsec:par5vpar7}

PAR-5 and PAR-7 both maintain state across inference steps.  The distinction
concerns the \emph{architectural role} of that state:

\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=2pt]
  \item \textbf{PAR-5 --- Memory is the primary representational structure.}
    In PAR-5 systems, the \emph{context IS the memory}: the entire design
    philosophy revolves around what information to persist, how to encode it,
    how to index it, and when to retrieve it.  The LLM is a consumer of the
    memory; the memory system is the first-class citizen.  Replacing the
    memory module with a flat context window would fundamentally change the
    system's identity.  Representative systems:
    \toolname{CodeMEM}~\cite{wang2026codemem},
    \toolname{LingmaAgent}~\cite{ma2025lingmaagent},
    \toolname{SWE-Exp}~\cite{chen2025sweexp},
    \toolname{Prometheus}~\cite{pan2026prometheus}.

  \item \textbf{PAR-7 --- Memory is a component of a larger agentic
    pipeline.}  In PAR-7 systems, memory (if present) is one tool among
    many: the agent may read from memory, write to files, execute tests, call
    APIs, and search the codebase, all within a single reasoning loop.
    Removing the memory component would reduce the agent's performance but
    would not alter its fundamental architecture.  The defining artefact of a
    PAR-7 system is the \emph{agent loop and its action space}, not any
    individual component.  Representative systems:
    \toolname{MetaGPT}~\cite{hong2023metagpt},
    \toolname{OpenHands}~\cite{wang2025openhands},
    \toolname{CodePlan}~\cite{bairi2024codeplan}.
\end{itemize}

\noindent\textbf{Classification rule.}  If the primary scientific contribution
of a paper is a novel \emph{memory representation or management strategy} for
code, the study belongs to PAR-5.  If the primary contribution is an
\emph{agent architecture, planning algorithm, or action-space design} that
happens to include a memory sub-module, the study belongs to PAR-7.

\section{Bidirectional Representation $\times$ Objective Mapping}
\label{sec:mapping}

\noindent\textbf{Research Question~3 (partial answer).}
Whereas Section~\ref{sec:taxonomy} characterised the seven paradigms along
structural dimensions, this section addresses RQ3 from the \emph{task
perspective}: \emph{Which representation paradigm best serves each SE
objective, and conversely, which objectives are best addressed by each
paradigm?}  The answer is grounded exclusively in the 168 primary studies of
our corpus; no claim is made about tools or results outside that set.

We organise the analysis as a \textbf{7~paradigms~$\times$~7~SE~objectives}
mapping matrix (Table~\ref{tab:mapping}).  Each cell records the

\textbf{\textsc{secondary}} (paradigm contributes to this objective but is
not dominant, 1--2 studies), or~\textbf{---} (no study in our corpus maps
this combination).  The subsections that follow provide detailed qualitative
evidence for each row.

\subsection{O1 --- Code Completion}
\label{subsec:o1}
%%─────────────────────────────────────────────────────────────────────────────

Code completion is the most studied SE objective in our corpus, with
contributions from all seven paradigms.  Two paradigms emerge as co-dominant.

\textbf{PAR-1 (primary).}
Dense embedding models are the historical foundation of repository-level
completion.  \toolname{LongCoder}~\cite{guo2023longcoder} extends the
transformer context window specifically to handle multi-file completion
scenarios.  \toolname{SECRET}~\cite{gu2025secret} demonstrates that segmented
deep hashing can scale embedding-based retrieval to industrial-scale
repositories, addressing the scalability limitation of flat FAISS
indices.  Hard-negative contrastive learning~\cite{fan2025hardneg} and
multi-granularity self-supervised pre-training~\cite{li2025mgs3} further
improve the quality of the embedding space for completion-specific queries.

\textbf{PAR-2 (primary).}
RAG cross-file retrieval is the second dominant paradigm for completion.
\toolname{RepoCoder}~\cite{zhang2023repocoder} establishes the
iterative retrieve-then-complete pipeline that remains a reference baseline.
\toolname{ReACC}~\cite{lu2022reacc} introduces the retrieve-augmented
completion framework.  Subsequent work optimises every component:
context filtering~\cite{sedov2025contextfilter},
adaptive segmentation~\cite{shen2025adaptiveseg},
multi-retrieval aggregation~\cite{tan2025multiretrieval},
context order and granularity~\cite{yusuf2025granularity},
type context injection~\cite{pan2025catcoder}, and
RAG vs.\ fine-tuning trade-off analysis~\cite{wang2025ragorfine,yang2025wechat}.
Code review assists via PAR-2 context are also reported by
\citeauthor{olewicki2026reviewassist}~\cite{olewicki2026reviewassist}.

\textbf{Other paradigms (secondary).}
PAR-3 contributions include \toolname{GraphCoder}~\cite{liu2024graphcoder}
(coarse-to-fine context retrieval using code context graphs),
\toolname{GRACE}~\cite{wang2025grace} (graph-guided hierarchical fusion), and
\toolname{RepoHyper}~\cite{phan2025repohyper}
(search-expand-refine on semantic graphs).
PAR-4 contributes \toolname{IRCoCo}~\cite{li2024ircoco} (RL with immediate
execution rewards).
PAR-5 contributes \toolname{AlignCoder}~\cite{jiang2025aligncoder}
(cross-file alignment) and \toolname{HyRACC}~\cite{li2025hyracc} (hybrid
memory-augmented retrieval).
PAR-6 contributes \toolname{LongCodeZip}~\cite{shi2025longcodezip} and
hierarchical context pruning~\cite{zhang2025hierctxpruning}.
PAR-7 contributes \toolname{RLCoder}~\cite{wang2025rlcoder} (RL-based
completion via repository exploration).

%%─────────────────────────────────────────────────────────────────────────────
\subsection{O2 --- Code Generation}
\label{subsec:o2}
%%─────────────────────────────────────────────────────────────────────────────

\textbf{PAR-2 (primary).}
Cross-file retrieval augmentation drives most repository-level code
generation work.  \toolname{CECoder}~\cite{he2025cecoder} retrieves fine-grained
code elements for generation.  \toolname{FastCoder}~\cite{zhao2025fastcoder}
accelerates generation via efficient retrieval and verification.
\toolname{RepoGenix}~\cite{liang2024repogenix} uses dual context-aided
completion.  \toolname{CATCODER}~\cite{pan2025catcoder} injects type context
from retrieved cross-file definitions.  Industry evaluations confirm PAR-2
scalability at WeChat's codebase~\cite{yang2025wechat} and beyond.

\textbf{PAR-7 (primary).}
Agentic systems have become co-dominant for code generation.
\toolname{MetaGPT}~\cite{hong2023metagpt} orchestrates multiple specialised
agents for end-to-end software development.
\toolname{CodePlan}~\cite{bairi2024codeplan} decomposes repository-level
coding tasks into sequential edit operations.
\toolname{CodeAgent}~\cite{zhang2024codeagent} uses tool-integrated agents for
real-world repository-level generation.
\toolname{A$^3$-CodGen}~\cite{liao2024a3codgen} combines local-aware,
global-aware, and task-aware retrieval in an agentic pipeline.
Specialised variants address context impacts~\cite{hai2025contextstudy},
context inlining for generation~\cite{hu2026contextinlining}, and
multi-agent debate for issue resolution~\cite{li2025swebdebate}.

\textbf{Other paradigms (secondary).}
PAR-3 contributes \toolname{CodexGraph}~\cite{liu2025codexgraph},
\toolname{GRACG}~\cite{fedorov2025gracg},
\toolname{RepoGraph}~\cite{ouyang2025repograph}, and knowledge-graph-guided
generation~\cite{athale2025kgcode,abedu2026llmskg}.
PAR-5 contributes \toolname{CodeMEM}~\cite{wang2026codemem} (AST-guided
adaptive memory for iterative code generation) and
\toolname{Prometheus}~\cite{pan2026prometheus} (long-horizon memory management).
PAR-6 contributes \toolname{CodeS}~\cite{zan2025codes} (multi-layer sketch),
\toolname{Hierarchical Summarisation}~\cite{dhulshette2025hiersumm}, and
\toolname{Context Engineering}~\cite{mohsenimofidi2026contexteng}.

%%─────────────────────────────────────────────────────────────────────────────
\subsection{O3 --- Code Search}
\label{subsec:o3}
%%─────────────────────────────────────────────────────────────────────────────

\textbf{PAR-1 (primary).}
Dense embedding models are the natural representation for code search, where
semantic similarity in a shared vector space is the fundamental operation.
\toolname{CodeBERT}~\cite{feng2020codebert} and
\toolname{GraphCodeBERT}~\cite{guo2021graphcodebert} establish the bimodal
pre-training paradigm.  Hard negative
mining~\cite{fan2025hardneg} significantly improves retrieval precision for
code search.  Zero-shot cross-domain search via
summarisation~\cite{liang2025zeroshot} shows PAR-6--PAR-1 synergy.
Repository-prompt generation~\cite{shrivastava2023repoprompt} and
\toolname{SpareCodeSearch}~\cite{nguyen2025sparecodesearch} address
low-resource GPU scenarios.

\textbf{PAR-3 (primary).}
Graph-based representations provide a complementary structural perspective
for search.  \toolname{CoSrch}~\cite{xu2025cosrch} combines syntactic AST
structure with semantic embeddings for effective code search.
\toolname{MGS3}~\cite{li2025mgs3} introduces a multi-granularity
self-supervised search framework.  \toolname{AskGraph}~\cite{yang2025askgraph}
enables dependency-aware search via LLM-generated Cypher queries over a code
graph.  \toolname{LiSSA}~\cite{fuchss2025lissa} applies
retrieval-augmented generation for generic traceability link recovery, which
requires cross-artifact code search.

\textbf{PAR-2 (secondary).}
\toolname{Code Search Is All You Need}~\cite{chen2024codesearch} demonstrates
that code search quality directly drives the quality of RAG-based completions,
establishing the link between PAR-1/PAR-3 search quality and PAR-2
generation quality.

%%─────────────────────────────────────────────────────────────────────────────
\subsection{O4 --- Bug Fixing and Issue Resolution}
\label{subsec:o4}
%%─────────────────────────────────────────────────────────────────────────────

Bug fixing is the objective with the \emph{most diverse paradigm coverage}
in our corpus.  Three paradigms achieve primary status.

\textbf{PAR-7 (primary).}
Agentic systems dominate the issue-resolution leaderboards
(\toolname{SWE-bench}~\cite{jimenez2024swebench}).
\toolname{SWE-agent}~\cite{yang2024sweagent} introduces the agent--computer
interface, giving the LLM shell access to reproduce, localise, and patch bugs.
\toolname{AutoCodeRover}~\cite{zhang2024autocoderover} adds AST navigation and
spectrum-based fault localisation to the agent loop.
\toolname{RepairAgent}~\cite{bouzenia2025repairagent} is a fully autonomous
repair agent.
\toolname{SWE-Search}~\cite{antoniades2024swesearch} applies Monte Carlo Tree
Search over the space of repository edits.
\toolname{AgentFL}~\cite{qin2025agentfl},
\toolname{OrcaLoca}~\cite{yu2025orcaloca}, and
\toolname{SWE-Exp}~\cite{chen2025sweexp} (experience-driven memory) are
further representative systems.  
\toolname{LingmaAgent}~\cite{ma2025lingmaagent} improves issue resolution via
comprehensive repository exploration with hierarchical memory.

\textbf{PAR-4 (primary).}
Execution-trace and dynamic feedback paradigms are essential for test-driven
bug fixing.  \toolname{RAP-Gen}~\cite{wang2023rapgen} retrieves analogous
patches and ranks repairs via execution outcomes.
\toolname{Rete}~\cite{parasaram2023rete} learns namespace representations
from runtime program repair traces.
\toolname{Iterative Refinement with Compiler Feedback}~\cite{bi2024iterrefine}
injects compiler signals as dynamic context.
\toolname{Trace}~\cite{tu2025trace} extracts context from test execution
traces to repair failing tests.
\toolname{Fact Selection}~\cite{parasaram2025factselect} explicitly quantifies
the contribution of dynamic facts in PAR-4 repair scenarios.

\textbf{PAR-3 (primary).}
Graph-based localisation and repair are the third dominant strand.
\toolname{LocAgent}~\cite{chen2025locagent} uses code graphs to guide
LLM-based fault localisation to the relevant files.
\toolname{Issue Localisation via Code Graph}~\cite{jiang2025issueloc}
searches iteratively over a code graph.
\toolname{Artifact-Integrated Bug Localisation}~\cite{feng2025buglocarti}
integrates heterogeneous software artefacts (graphs, history, tests).
\toolname{Knowledge-Enhanced Bug Localisation}~\cite{li2025knowledgebug}
augments the LLM with a structured knowledge base.
Impact analysis using program dependence
graphs~\cite{yan2024impactanalysis} supports change-impact-based repair
planning.

\textbf{PAR-2 and PAR-5/6 (secondary).}
PAR-2 contributions include \toolname{Back to Basics}~\cite{huang2025issuecommit}
(LLM-assisted issue-commit linking) and
\toolname{SWE-GPT}~\cite{ma2025swegpt}.
PAR-5 contributes the experience replay in \toolname{SWE-Exp}~\cite{chen2025sweexp}.
PAR-6 contributes \toolname{Natural Language Summarisation for Bug
Localisation}~\cite{oskooei2025nlsumm} (microservice context).

\subsection{O5 --- Refactoring and Code Translation}
\label{subsec:o5}
%%─────────────────────────────────────────────────────────────────────────────

\textbf{PAR-7 (primary).}
\toolname{RefAgent}~\cite{oueslati2026refagent} is the first multi-agent
LLM-based framework specifically designed for automatic software refactoring,
combining structural analysis, test validation, and iterative agent loops.
\toolname{Divide-and-Conquer}~\cite{wang2025divideconquer} automates code
revisions via localisation-and-revision agent pairs.
\toolname{LLM Fusion for Code Change}~\cite{dilhara2024fusionllms}
demonstrates transformation-by-example driven agentic refactoring.
For translation, \toolname{Scalable Code Translation}~\cite{zhang2025scalabletrans}
validates entire project-level translation through agentic verification loops;
\toolname{C-to-Rust Translation with RL}~\cite{feng2026ctorust} uses
reinforcement alignment in an agentic setting.

\textbf{PAR-3 (primary).}
\toolname{AlphaTrans}~\cite{ibrahimzada2025alphatrans} is the canonical
PAR-3 contribution to translation: it exploits the call graph and data-flow
dependencies to decompose the translation problem compositionally.
\toolname{Cross-Lingual Semantic Graphs}~\cite{jiang2024crosslinggraph}
retrieves cross-lingual semantic graphs for code generation with translation
intent.
\toolname{Dependency Breaking Changes}~\cite{fruntke2025depbreaking} uses
dependency graph analysis to automatically fix breaking changes.

\textbf{PAR-4 (secondary).}
Execution-feedback-driven repair of translation
artefacts~\cite{parasaram2023rete,bi2024iterrefine} supports PAR-3 and PAR-7
pipelines as a secondary mechanism.

%%─────────────────────────────────────────────────────────────────────────────
\subsection{O6 --- Test Generation}
\label{subsec:o6}
%%─────────────────────────────────────────────────────────────────────────────

\textbf{PAR-7 (primary).}
Test generation is the SE objective where PAR-7 is most clearly dominant,
with no other paradigm achieving primary status.
\toolname{CoverUp}~\cite{altmayer2025coverup} uses an LLM agent to
iteratively improve Python test coverage by analysing coverage reports and
generating targeted tests.
\toolname{CITYWALK}~\cite{zhang2025citywalk} addresses C++ unit test
generation via project-dependency-aware agentic exploration.
\toolname{KTester}~\cite{li2026ktester} combines domain knowledge and testing
knowledge in an agent loop for more effective test generation.
\toolname{Issue2Test}~\cite{nashid2026issue2test} generates reproducing test
cases from issue reports using agentic context exploration.
\toolname{LSPRAG}~\cite{go2025lsprag} uses LSP-guided RAG within an agent
loop for real-time unit test generation across multiple languages.
\toolname{SAINT}~\cite{pan2025saint} generates integration tests via program
analysis and LLM-based agents.
\toolname{ChatUniTest}~\cite{chen2024chatunitest} provides a foundational
LLM-based test generation framework.

\textbf{PAR-4 (secondary).}
Execution-trace feedback plays a supporting role: \toolname{Trace}~\cite{tu2025trace}
uses test execution traces to repair (and thereby improve) failing tests.
\toolname{SWE-Gym}~\cite{pan2025swegym} provides an execution-reward
environment used for training test-generation agents.
\toolname{Reference-Based Retrieval-Augmented Unit Test Generation}~\cite{zhang2025refbasedtest}
combines PAR-2 retrieval with PAR-4 test-execution feedback.

\textbf{PAR-3 (secondary).}
\toolname{SAINT}~\cite{pan2025saint} exploits control-flow graphs alongside
the agentic loop, and \toolname{CITYWALK}~\cite{zhang2025citywalk} uses
project dependency analysis (a graph-based mechanism) to inform test
generation---illustrating frequent PAR-3/PAR-7 hybrid deployment.

%%─────────────────────────────────────────────────────────────────────────────
\subsection{O7 --- Code Review}
\label{subsec:o7}
%%─────────────────────────────────────────────────────────────────────────────

\textbf{PAR-2 (primary).}
Code review assistance is the SE objective with the narrowest paradigm
coverage in our corpus, with PAR-2 as the clear dominant paradigm.
\citeauthor{olewicki2026reviewassist}~\cite{olewicki2026reviewassist} conduct
a mixed open/closed-source case study evaluating the practical impact of an
LLM-based review assistant that retrieves relevant code context (PAR-2) to
generate inline review comments.  Their study demonstrates that cross-file
context retrieval is the critical enabler for non-trivial review feedback that
goes beyond syntactic checks.

\textbf{PAR-6 (secondary).}
\toolname{Natural Language Summarisation}~\cite{oskooei2025nlsumm} and
\toolname{ArtifactSync}~\cite{alor2026artifactsync} use compression and
hierarchical summaries of the repository state, which are natural inputs for
review assistants that must surface high-level change impact without exposing
the full diff to the LLM.

\textbf{PAR-7 (secondary).}
Agentic approaches such as \toolname{SWE-Debate}~\cite{li2025swebdebate}
and \toolname{Ensemble Reasoning}~\cite{tian2026agentensemble} implicitly
perform review-like activities (checking correctness, consistency with
requirements) as part of their issue-resolution loops, though review is not
their primary objective.

\textbf{Discussion.}
The relative under-representation of code review in our corpus is itself a
finding: despite the practical importance of automated review, only one study
(\citeauthor{olewicki2026reviewassist}) explicitly targets O7 as its primary
SE objective.  This constitutes a significant research gap, particularly for
PAR-3, PAR-4, and PAR-5 paradigms, none of which appear in the corpus with
review as a primary objective.

%%─────────────────────────────────────────────────────────────────────────────
\subsection{Summary of Mapping Findings (RQ3, Partial)}
\label{subsec:mappingsummary}
%%─────────────────────────────────────────────────────────────────────────────

\begin{mdframed}[backgroundcolor=gray!8, linewidth=0.4pt, innerleftmargin=6pt,
                 innerrightmargin=6pt, innertopmargin=4pt, innerbottommargin=4pt]
\textbf{Answer to RQ3 (paradigm--objective mapping component).}
No single paradigm dominates across all seven SE objectives.  The mapping
reveals three structural patterns:
\begin{enumerate}[leftmargin=*,topsep=2pt,itemsep=2pt]
  \item \textbf{Objective concentration}: PAR-7 achieves primary status on
    the widest range of objectives (O2, O4, O5, O6), reflecting the
    generality of the agentic interface; PAR-1 concentrates on O1 and O3;
    PAR-2 spans O1--O2 and is the sole primary paradigm for O7.
  \item \textbf{Paradigm specialisation}: O3 (code search) is uniquely
    addressed by PAR-1 and PAR-3 only; O7 (code review) is uniquely
    addressed by PAR-2 as a primary paradigm; O6 (test generation) is almost
    exclusively in the PAR-7 domain.
  \item \textbf{Multi-paradigm objectives}: O4 (bug fixing) is the only
    objective with three co-dominant paradigms (PAR-3, PAR-4, PAR-7),
    reflecting the multi-faceted nature of fault localisation and repair.
\end{enumerate}
These findings motivate the formal trade-off analysis in
Section~\ref{sec:evaluation}, where we compare representative systems from
the dominant paradigms for each objective on public benchmarks.
\end{mdframed}

\section{Discussion}
\label{sec:discussion}
%%══════════════════════════════════════════════════════════════════════════════

\subsection{Paradigm Coverage and Complementarity}

Our seven-paradigm taxonomy reveals that most state-of-the-art systems combine
elements from multiple paradigms: e.g., a PAR-7 agent may query a PAR-3 graph
database and maintain a PAR-5 memory buffer.  The taxonomy captures the
\emph{primary representational commitment} of each work, not the absence of
secondary mechanisms.

\subsection{Training Dependency as a Practical Lens (D10)}

The revised dimension D10 highlights a critical engineering trade-off.  While
Full RL (Level~3) systems such as \toolname{SWE-RL}~\cite{wei2025swerl} and
\toolname{RLCoder}~\cite{wang2025rlcoder} achieve strong benchmark performance,
they require substantial compute and curated execution environments.
Zero-shot (Level~0) approaches remain competitive for many tasks when combined
with effective retrieval or graph-based context (PAR-2/PAR-3), as demonstrated
by \toolname{CodexGraph}~\cite{liu2025codexgraph} and
\toolname{RepoGraph}~\cite{ouyang2025repograph}.  Practitioners should select
their training dependency level based on available resources and the target SE
objective.

\subsection{Open Challenges}

\begin{enumerate}[leftmargin=*,topsep=2pt,itemsep=2pt]
  \item \textbf{Scalability.}  Most PAR-3 and PAR-7 systems have been
    evaluated on single-repository benchmarks.  Scaling to
    multi-repository~\cite{oskooei2025nlsumm} or monorepo settings remains
    an open challenge.
  \item \textbf{Multilingual support.}  Benchmarks such as
    M2RC-EVAL~\cite{liu2025m2rceval}, Multi-SWE-Bench~\cite{zan2025multiswe},
    and OmniGIRL~\cite{guo2025omnigirl} expose significant performance gaps
    across programming languages.
  \item \textbf{Evaluation standardisation.}  The diversity of benchmarks
    (Table~\ref{tab:benchmarks}) hampers direct comparison.  A unified
    evaluation harness covering all seven SE objectives is needed.
  \item \textbf{Context faithfulness and hallucination.}  All paradigms are
    susceptible to generating plausible but incorrect code.  The
    fact-selection problem~\cite{parasaram2025factselect} is particularly
    acute in PAR-3.
  \item \textbf{Privacy and security.}  Repository-level context may contain
    sensitive information; privacy-preserving retrieval and on-device inference
    are under-explored.
\end{enumerate}

%%══════════════════════════════════════════════════════════════════════════════
\section{Threats to Validity}
\label{sec:threats}
%%══════════════════════════════════════════════════════════════════════════════

\paragraph{Internal validity.}
The classification of each study into one of seven paradigms was performed
by two independent coders with a Cohen's $\kappa > 0.80$.  Disagreements
were resolved by discussion and, where needed, majority vote among three
reviewers.

\paragraph{External validity.}
Our search covered major SE, AI, and NLP venues through April~2026.  Rapidly
evolving technical reports and grey literature may have been missed despite
our arXiv inclusion criteria.

\paragraph{Construct validity.}
The ten dimensions were derived inductively from the corpus; alternative
dimension sets are possible.  The revised D10 label \emph{Training Dependency}
is a conceptual consolidation grounded in the observed distribution of
approaches, not a formal ontology.

\section{Related Work}
\label{sec:relwork}
%%══════════════════════════════════════════════════════════════════════════════

Several surveys address adjacent topics.
\citet{hou2024llmsslr} provide a comprehensive SLR of LLMs for software
engineering but do not focus on repository-level context representation.
\citet{jiang2026surveyllm} survey LLMs for code generation with emphasis on
task benchmarks rather than representation strategies.
\citet{tao2026ragsurvey} survey retrieval-augmented code generation with a
focus on RAG techniques (our PAR-2) but do not cover PAR-3 through PAR-7.
\citet{husein2025codecompletion} review LLMs for code completion without
cross-file context as a primary concern.
\citet{zhang2026surveyllmse} cover the broader LLM-for-SE landscape.

Our work complements and extends these surveys by providing a unified taxonomy
covering all seven paradigms, the cross-paradigm disambiguation (PAR-4/7 and
PAR-5/7), and the revised Training Dependency dimension~(D10).

%%══════════════════════════════════════════════════════════════════════════════
\section{Conclusion}
\label{sec:conclusion}
%%══════════════════════════════════════════════════════════════════════════════

We have presented a systematic literature review of 168 studies on
repository-level context representation for LLM-based software engineering.
Our seven-paradigm taxonomy (PAR-1--PAR-7) provides the first unified
framework for classifying and comparing this rapidly growing body of work.
Key contributions include:

\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=2pt]
  \item \textbf{D10 --- Training Dependency}: a revised taxonomy dimension
    distinguishing Zero-shot, RAG-only, Lightweight FT, and Full RL,
    replacing the coarser \emph{Fine-Tuning Requirements} label.
  \item \textbf{PAR-3 sub-types}: an explicit categorisation into five
    graph families (AST, CFG, Call Graph, DFG, Knowledge Graph).
  \item \textbf{PAR-4 vs.\ PAR-7 disambiguation}: passive trace recording
    vs.\ active agent exploration.
  \item \textbf{PAR-5 vs.\ PAR-7 disambiguation}: memory as the primary
    representation vs.\ memory as a pipeline component.
\end{itemize}

We make the full dataset, annotation guidelines, and extracted data available
as supplementary material to foster reproducibility and future research.
